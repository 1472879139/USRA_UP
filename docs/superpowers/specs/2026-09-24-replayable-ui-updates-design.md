# 可重放界面进度设计

## 目标与范围

在不改动 Agent 框架、模型调用和分析算法的前提下，消除网页轮询“读走消息”、刷新后丢失聊天、重复确认让页面假装就绪的问题。仅保证同一个 Flask 进程内的会话恢复；重启服务后聊天事件仍是内存态，结果文件及已导出的记录不变。

## 已确认的问题

- `/api/updates` 当前从 `ui_queue` 取走事件，第二个页面或诊断请求会抢走第一个页面的消息。
- 前端先乐观显示用户输入，后端消息总线也产生同一条用户消息；刷新页面又没有历史回放。
- 后端正忙时 `/api/chat` 返回 `success=false`，前端却一律设置“就绪”并停止轮询。
- 轮询响应中的旧 `done` 事件可能盖过后台正在运行的真实状态。

## 后端协议

保留 `ui_queue` 作为后台线程的生产者队列；Flask 控制器在锁内将其一次性转入**内存事件日志**。日志中的可见消息带单调递增的 `seq`。`GET /api/updates?since=N` 返回当前会话日志中 `seq>N` 的事件，读取不会删除日志。响应同时返回最新 `cursor`、`running`、`phase`、`done`、`waiting_confirm`、`status`、监控和追溯面板。状态来自当前会话及运行标志，而不是某次取出的旧 `done` 事件。

序号在进程内持续递增；开始新分析或新对话时清空当前日志，但不重置序号。这样旧浏览器的游标不会压过新会话事件。新页面以 `since=0` 请求当前日志即可恢复。日志只保留当前会话，不保存 API 密钥或完整模型提示词。

接收 `/api/chat` 后，服务端为**已接受**的用户输入（包括 `approve`）记录一条可见事件；消息总线回送的 User 事件不再重复记录。正忙拒绝返回明确的 `busy: true`，不启动第二条分析链。失败或完成状态要由响应快照准确反映。

## 前端行为

浏览器保存最后处理的 `cursor`，每次轮询带上 `since`；同一时刻只允许一个进度请求。用户输入仅由服务端事件显示，避免本地显示与回放重复。提交中的确认按钮立即禁用，避免双击。若提交得到 `busy: true`，页面继续轮询当前任务而非显示“就绪”；其他拒绝才恢复空闲。网络异常后继续查询服务端状态，因为提交是否被接受可能未知。

浏览器刷新时游标从 0 开始，重放当前会话事件；完成或等待 Manager 确认后停止轮询，下一次成功提交再启动。不会自动重试任何付费模型调用。

## 验收

1. 两个客户端用 `since=0` 都能读到同一条消息；用最新游标再次请求不会重复收到它。
2. 刷新页面能重建当前会话的用户输入、Agent 回复和错误消息。
3. 正忙拒绝与迟到的旧轮询响应不会使运行中的页面显示“就绪”或停止更新。
4. 双击确认不会启动第二次分析；完成、等待确认和失败状态均由服务端一致表达。
5. 离线 Python 和 Node 回归测试通过；不触发真实 LLM 调用。
