# Manager 修改意见上下文保留设计

## 目标与范围

修复手动确认阶段输入修改意见时，应用将其当作新请求，导致会话重建、原始需求丢失的问题。不恢复结构化任务单；不改变一键托管的流程或入口。首轮 Manager 重复追问已给条件的模型行为不在本次代码修复范围内。

## 当前故障

`URSAGUI.start_analysis()` 对任何非确认文本都清空消息、创建新 Agent 和 Session。随后 `ManagerAgent.handle_message()` 将修改意见覆盖到 `session.user_request`，确认时只把这一条文本交给 Scientist。由此，原始区域、分类、数据文件或输出要求可能在多轮修订后消失。

## 设计

1. 在 `MANAGER_CONFIRM` 阶段接收普通文本时，沿用当前 Session、Agent 与可回放的 UI 历史；只有真正的新任务才初始化新会话。一键托管原有分支不变。
2. `session.user_request` 保留首次用户需求原文。新增按时间顺序记录的修改意见，不用修改意见覆盖原文。Manager 每轮修订提示显式包含原始需求、此前修改意见、上次确认摘要及本轮意见，并要求只追问仍缺失的信息。
3. Manager 生成新确认摘要后，将其作为辅助说明保存；用户原文和修改意见始终是权威来源。若 Manager 调用失败，保持现有错误处理，不把错误当作确认计划。
4. 用户输入 `approve` 时不额外调用模型。向 Scientist 传递原始需求、按顺序排列的修改意见和 Manager 最新确认摘要；明确“后续明确修改覆盖先前冲突条件，未被修改的条件保持不变”，且不把 `approve` 当需求。
5. 不宣称这能证明模型语义理解必然正确；它保证信息完整交接，并通过离线测试核对原文、修订顺序和传递边界。

## 验证

- 初始请求 → 一次或多次修改意见 → 确认：Session 与 Agent 不重建，原始需求保留，消息仍可回放。
- 每轮 Manager 提示含原始需求和有序修订；本轮意见不覆盖 `user_request`。
- Scientist 收到原始需求、全部修改意见、最新确认摘要和覆盖规则，不收到作为任务内容的 `approve`。
- 无修改意见时维持现有原文交接；Manager 失败与一键托管现有测试保持通过。
- 测试不调用付费模型或远程 API。
